## 4. Cleaning

Rows 6,362,620 → **6,362,335**; positive labels 8,213 → **7,928**.
Actions: `drop_rows` removes rows, `drop_column` removes a column, `transform` changes values, `flag` documents an issue that is kept on purpose.

| # | rule | action | rows | positives | rationale |
| --- | --- | --- | --- | --- | --- |
| 1 | `invalid_values` | drop_rows | 0 | 0 | Rows that don't match the documented schema (nulls, unknown type, negative amount, label outside {0,1}) can't be mapped to the event contract. |
| 2 | `exact_duplicates` | drop_rows | 0 | 0 | An identical row twice is a load artefact, not two transactions (keep the first). |
| 3 | `zero_amount` | drop_rows | 16 | 16 | A transaction that moves no money is not a transaction. In PaySim all of them are labelled fraud (attempts on already-emptied accounts), so they would teach the model 'amount = 0 → fraud', a simulator artefact. |
| 4 | `simulation_tail` | drop_rows | 269 | 269 | Days with no legitimate traffic at all are the simulator still emitting fraud after normal activity stopped (100 % fraud). They would dominate a time-based test set and make evaluation meaningless. |
| 5 | `drop_isFlaggedFraud` | drop_column | 0 | 0 | The simulator's own rule (transfers > 200k) fired 16 times in 6.3 M rows. It is not an input a bank would have, and as a label proxy it would leak. |
| 6 | `origin_balance_inconsistent` | flag | 3,678,404 | 42 | Kept: the simulator often doesn't update origin balances. Only `oldbalanceOrg` feeds a feature (`balance_drain_ratio`), and only when > 0. |
| 7 | `destination_balance_not_updated` | flag | 5,640 | 3,934 | Kept for lineage but excluded from all features: ~50 % of fraud vs ~0.03 % of legitimate transfers have both destination balances at 0 (simulator leak). |
| 8 | `fraud_rate_inflated_period` | flag | 414,021 | 4,167 | Kept: days whose fraud share exceeds 3x the overall rate. The simulator injects fraud at a ~constant count per day while legitimate volume swings (1k-574k rows/day), so these shares are an artefact, not a pattern to learn. Measured by the `time` ablation and visible in the daily profile. |

## 5. Mapping to the platform contract (`TransactionEvent` v1)

| raw | canonical | transformation |
| --- | --- | --- |
| (raw row number) | transaction_id | `PS-<row>`, traceable to the raw file line |
| step | event_time | 2026-01-01T00:00Z + (step-1) h + deterministic offset in the hour |
| nameOrig | customer_id, source_account | PaySim has one account per customer |
| nameDest | destination_account | `M…` = merchant |
| type | transaction_type | same five values |
| amount | amount | 2 dp; currency `XXX` (ISO 4217: no currency; PaySim has none) |
| oldbalanceOrg/newbalanceOrig/oldbalanceDest/newbalanceDest | balances | kept for lineage; destination balances are **not** used by any feature (leak) |
| isFraud | is_fraud_label; scenario | scenario = `fraud_<type>` or `normal` |
| isFlaggedFraud | - | dropped (see cleaning) |
| - | device_id, ip_address, location | absent in PaySim: left empty, not invented |

## 8. Limitations

- Synthetic (simulated from aggregated real logs), not real customer data.
- `nameOrig` is ~99.9 % unique: almost every customer appears once, so per-customer history/velocity features are near-constant on PaySim.
- No device, IP or location: network features are empty on PaySim.
- Fraud is injected at a ~constant rate per day while legitimate volume varies strongly, so fraud *rates* in low-volume periods are a simulator artefact (see the `time` ablation).
- Fraud almost always empties the origin account (`balance_drain_ratio` ≈ 1): a strong signal that is partly a simulator design choice (see the `balance` ablation).
